# Gaps in the scaffold and the tracker

Found while building softory on scaffold **1.4.0** (`172df83`) and the tracker at **`ee3dee6`**. Each gap lists what softory does in the meantime and a suggested fix upstream. They're ordered by impact.

## Fixed in scaffold 1.4.1

Scaffold **1.4.1** (`9e534a6`, tag `v1.4.1`, the schema-1 `1.x` branch) fixed fifteen of the gaps below, and its tags and maintenance branch settle S7 and S8. Softory 0.3.1 pins it. Schema version 1 is unchanged, so an upgrade needs no migration; softory's installer backs the database up first anyway.

| Gap | What 1.4.1 added | What softory does now |
| --- | --- | --- |
| S1, S2 | `closure_policy: strict` and `dependency_policy: strict` in `.coordination/config.yml`, both off by default | Leaves both off. Strict closure would refuse review records and dropped work, and strict dependencies would refuse stacked work (S24). `softory close` still runs the gate. |
| S3 | `--no-gitignore` and `--ignore-file` on the installer | Passes `--no-gitignore`; the `.gitignore` snapshot and restore are gone. |
| S6 | `agent update` edits the profile fields | Not used yet. Roles registered before softory, as in Vault Radar, keep their own profiles. |
| S7, S8 | Release tags, and a `1.x` branch for schema 1 | Pins the `v1.4.1` commit. |
| S9 | Repeatable `task list --tag` with AND | Not needed yet; softory still filters in Python. |
| S10 | Review rows carry `sequence`, and `review list` sorts by it | Sorts by `sequence`. `task show` still sorts by second and then ID (S23), so softory re-reads a task's reviews from `review list` when two share a second. |
| S11 | `doctor` reports the database's filesystem and FUSE leftovers | `softory doctor` shows these under `warnings`; they never fail it. |
| S12 | `COORDINATION_DB`, and discovery from a linked worktree | Softory ignores an inherited `COORDINATION_DB`, so the project it runs in decides the database. |
| S13 | `health` lists `tasks_with_accepting_reviews` | `softory triage` still lists them, with the gate's view. |
| S16 | `inbox count` and `audit activity` | Not used yet; `softory pending` still composes its answer. |
| S17 | `dependency list` | Not used yet. |
| S19 | `task claim --no-assign` | Claims to close or drop use it, so the closer never becomes a builder. |
| S20 | `decision add --recorded-by` | `softory ruling` and `softory propose` use it: the decision stays the owner's, and the audit row names the role that recorded it. |
| S21 | The AGENTS block marks the inbox read with the listing's `head` | Picked up on install. A project that commits its own `AGENTS.md` keeps its older block, so the Codex override swaps in the installed one and `doctor` warns. |
| S22 | `next_offset` on full pages | `softory all` keeps paging until a short page, which still works. |

Still open: S4, S5, S14, S15, S18, and the new S23 and S24.

## Scaffold (agentic-project-scaffold-lite 1.4.0)

| # | Gap | Impact | Softory's workaround | Suggested fix |
| --- | --- | --- | --- | --- |
| S1 | **Any active actor can close any task.** `review → done` is an unowned transition. It needs evidence, but no accepted review, no check of open `blocks` dependencies, and no rule about who may close. Verified: Toby closed Greg's story while a blocking child was still `todo` and no review existed. | Role boundaries and review gates are honor-system only | `softory close` runs the gate (reviews, self-review, dependencies, children, closer) before moving to `done`. Agents are told to close only through it, but a raw `task status done` still works. | A closure policy: optionally require an accepted review from a non-assignee and resolved `blocks`/`review_required` dependencies before `done`. Or a pre-transition hook softory can plug its gate into. |
| S2 | **`blocks` dependencies are advisory.** `task claim` and `task status` never check them. | Work can start before what it depends on is done | `softory gate` checks them at close. The operating-loop skill says not to claim blocked work. | Reject `claim` (or warn in the envelope) while an active `blocks` dependency points at a task that isn't `done`. |
| S3 | **The SQLite installer edits the target's tracked `.gitignore`** with no opt-out. | Installing makes a visible, committable change | Softory snapshots `.gitignore` and restores it byte for byte after the scaffold installer runs, then hides everything with `.git/info/exclude`. | `--ignore-file PATH` (for example `.git/info/exclude`) or `--no-gitignore`. |
| S4 | **No task hierarchy or task kind.** There's no parent field and no epic, story, or task type. | Units of work have to be encoded by convention | `unit:*` and `parent:*` tags, `PREFIX-n` IDs, and a `blocks` dependency from parent to child. `softory tree` renders the hierarchy. | A `parent_id` and a `kind` field (or a `contains` dependency type), with rollups in `summary` and `health`. |
| S5 | **Long-lived parents can't be "in progress".** A claim is a one-hour lease, and the session sweep blocks claimed tasks whose session goes quiet. | Epics and stories can't show as active for days | Epics and stories stay `todo` while children run. Greg claims them only briefly to close them. | An `active` state that isn't a claim, or a per-task lease length. |
| S6 | **`agent update` can't change profile text.** Only name, role, actor type, and status are editable. | Improved role definitions can't reach agents already registered | Re-installing leaves existing agents untouched and reads profiles from files instead. | Accept `--responsibilities`, `--decision-authority`, and the other profile fields on `agent update`. |
| S7 | **No release tags.** The repo has `VERSION` files and changelog entries but no git tags. | Consumers pin by commit hash | Softory pins `172df835…` in `dependencies.json`. | Tag `v1.4.0` and `v2.0.0`. |
| S8 | **`main` is 2.0.0, but the tracker needs a CLI below 2.0.0.** | Installing from `main` breaks the tracker | Softory pins 1.4.0 and refuses a 2.x checkout. | Update the tracker for schema 2, or keep a `1.x` maintenance branch. |
| S9 | **`task list --tag` takes one tag.** | Can't ask for "unit:task AND lane:frontend" in one call | Softory filters in Python after one tag-filtered call. | Make `--tag` repeatable with AND semantics, like `--status`. |
| S10 | **Same-second review ordering.** Reviews sort by `created_at` (to the second) then by ID text, so `REV-10` sorts before `REV-9`. | "Latest review wins" can pick the wrong one in a tight loop | Softory uses the CLI's order and recommends unique, time-ordered review IDs. | Expose the audit sequence on review rows, or sort by it. |
| S11 | **Nothing stops the database being shared across a VM or mount boundary.** The SQLite backend uses WAL mode, which needs every process on one host. VaultRadar's `.coordination/` holds `.fuse_hidden*` files left by processes that reached the database through a VM's FUSE mount. | Risk of a corrupt or inconsistent database when an agent in a VM or container works on a host folder | Softory's README says to install and run on the machine that runs the agents. | `doctor` warns when `.coordination/` is on a FUSE or network filesystem, and the docs say so. |
| S12 | **Tools in a worktree outside the repository can't find the database.** Discovery walks up from the current directory, refuses a symlinked `.coordination`, and there's no environment variable for the database path. | An agent in a sibling worktree, or Codex's own worktree folder, can't run coordination commands | `softory coord` runs the CLI from the main checkout. | A `COORDINATION_DB` (or `COORDINATION_ROOT`) environment variable, or resolving the main worktree through `git rev-parse --git-common-dir`. |
| S13 | **An accepted review doesn't move the task.** In VaultRadar, four sampled "todo" tasks had accepted reviews of merged fixes, so the work was done but never closed. | Backlogs fill with finished work, and agents re-plan or rebuild it | `softory triage` lists open tasks with an accepted review. | A `review add` option, or a health warning, for tasks whose latest reviews all accept them while they're still open. |
| S14 | **Reviews aren't claimable work.** A review is a record written in one call; there's nothing to claim, heartbeat, or attach a report to while it runs. In VaultRadar, Avery and Toby made a task per review run instead: 61 in two days, most with the verdict recorded on the run itself and the fixes in `follow_up_tasks`. | Review runs pile up as open tasks, and a gate that treats them as code asks for a review of the review and is blocked by the run's own verdict | Softory's review record (`unit:review`): its verdicts are output, not a block, and it closes once every requested change names a follow-up task that exists. | A review request with a claim and lease (`review start --task X`, then `review add` completes it), or let evidence attach to a review. |
| S15 | **`review add` doesn't touch the task.** Its `updated_at` and `revision` stay put: in VaultRadar, EPIC-1's `updated_at` stayed at 14:16 while Toby's and Quinn's sign-offs landed at 14:19 and 14:38. | Anything that watches tasks for change misses new reviews | `softory pending` joins every review's `created_at` onto its task. | Bump the task's `updated_at` (or add a `last_activity_at`) when a review, evidence row, or dependency is added. |
| S16 | **No way to ask "anything new for me?" without a model.** There's no unread count and no activity-since query, so a scheduled role starts a full agent run to find out. Greg's 188 five-minute runs in VaultRadar did nothing 165 times. | Idle runs cost tokens all day | `softory pending <role>` composes it from `inbox list`, `session list`, `task list`, and `review list`. | `inbox count --agent X` and `activity --agent X --since T`, both cheap and read-only. |
| S17 | **Dependencies can only be read one task at a time,** through `task show`. There's no `dependency list`. | Gating many tasks costs one CLI call per task | `softory queue` filters on list data first and calls `task show` only for likely candidates. | `dependency list` with `--where`, like the other list commands. |
| S18 | **No way to close work nobody will build.** `done` is reachable only from `review`, `review` only through a claim, and there's no cancelled or won't-do status. | Dropped tasks stay open forever, or get closed with fake evidence | `softory drop` records a decision, adds it as evidence, tags `resolution:`, and walks claim, review, done, then takes back the claimant's assignment. | A `cancelled` status (or `done --resolution wont_do`) reachable from any open status, with a required reason. |
| S19 | **A claim makes the claimant an assignee, permanently.** `task claim` inserts the claimant into `task_assignees` and release doesn't remove it. | Anyone who claims a task to move it, a reviewer or the owner, counts as one of its builders from then on, which changes who may review it | Softory removes the assignment it caused when it claims to drop or close a record. | Record assignment and claim separately, or remove an assignment the claim added when the claim ends. |
| S20 | **Recording someone else's decision fails in a session.** `decision add --owner owner` from a role's session fails with `session_actor_mismatch`, and decisions have no recorded-by field. | Agents log the owner's rulings under their own name, as Quinn did in Vault Radar | `softory ruling` records it without a session, owned by the owner, with "recorded by <role> (<session>)" and where the owner said it in the context. | A `--recorded-by` field on decisions, filled from the session. |
| S21 | **The scaffold's own instructions don't match its CLI.** The AGENTS block says `inbox mark-read --cursor HEAD`, but `--cursor` takes only a number, and the block never mentions `message show`. | Agents fail to mark their inbox read, and believe they can't show one message | `softory inbox` prints the exact `--mark-read N`, and `softory message <ID>` wraps `message show`. | Correct the block to use the `head` number from `inbox list` (a literal `HEAD` would also mark messages that arrived after the listing), and document `message show`. |
| S22 | **Lists stop at 500 rows with no total or next page.** | A caller can't tell a full page from the end | `softory all <entity> list` pages until a short page. | Return `total` or `next_offset` in list envelopes. |
| S23 | **`task show` still sorts reviews by `created_at` and then ID** (found on 1.4.1). Only `review list` sorts by `sequence`, and `task show`'s reviews carry no `sequence`. Verified: two reviews added in one second come back as REV-10 before REV-9. | Anyone reading "latest review" from `task show` can take an accept as the last word when a request for changes followed it in the same second | Softory re-reads the task's reviews from `review list --order-by sequence:asc` whenever two share a second. | Sort `task show`'s reviews by rowid and include `sequence`, as `review list` does. |
| S24 | **The strict policies can't express softory's rules** (1.4.1). `closure_policy: strict` wants an accepted review on the task itself, so it refuses a review record (which closes on its own verdicts) and dropped work (which has none). `dependency_policy: strict` refuses a claim on work stacked on unfinished work. | S1 and S2 stay honor-system in softory projects | Both policies stay off; `softory close` runs the gate, and `softory triage` lists units that reached done without it. | Let strict closure accept a recorded `--because decision:<ID>` instead of a review (softory's drops already pass one), or add S18's `cancelled`, and exempt tasks tagged as records; or offer a pre-transition hook. Let strict dependencies take a dependency type that means "built on" without blocking a claim. |

## Tracker (agentic-scaffold-project-task-tracker, `ee3dee6`)

| # | Gap | Impact | Softory's workaround | Suggested fix |
| --- | --- | --- | --- | --- |
| T1 | **No installer or package.** `pyproject.toml` declares no distribution, and packaging is still open as UI-27. | Every consumer has to copy `coordination_ui/` by hand | Softory copies `coordination_ui/` into `.agents/softory/tracker/` and runs it with `PYTHONPATH` (`softory tracker`). | An `install.sh --target` that mirrors the scaffold's, or a wheel. |
| T2 | **No hierarchy view.** Epics, stories, and tasks show as a flat list, and `parent:` tags are just text. | Hard to see progress per epic or story | `softory tree` in the terminal | Group or indent by a `parent:` tag (or S4's field), with a unit filter and child counts. |
| T3 | **No release tags,** and the app reports `1.0.0` with no matching tag. | Pin by commit | Softory pins `ee3dee67…`. | Tag releases. |
| T4 | **CLI support stops below 2.0.0.** | See S8 | Pin 1.4.0 | Support schema 2, or document the 1.x branch. |
| T5 | **Reviews don't show gate status.** There's no "required reviewers" or self-review flag. | Operators can't see why a unit can't close | `softory gate` and `softory reviewers` | Optional: read a project-local gates file, or show a "reviewed by assignee" warning. |
| T6 | **No view of finished-but-open work.** There's no filter for open tasks whose latest review accepts them. | The tracker shows a large todo list that is mostly done | `softory triage` | A filter or health card: open tasks with an accepted latest review and no open rejection. |
| T7 | **Its tests expect CLI version `1.4.0` exactly.** Against scaffold 1.4.1, 510 of 514 tests pass at `ee3dee6`; the other four assert the version string. The console itself accepts `>=1.4.0,<2.0.0` and works. | Its suite reads as failing on any newer 1.x | None needed; softory doesn't run the tracker's tests. | Compare against `SUPPORTED_CLI_VERSION` or the installed CLI's version instead of a literal. |

S1 matters most. Scaffold 1.4.1 can now enforce closure, but not in a form that allows softory's review records and dropped work (S24), so softory's boundaries still hold only as long as agents follow the operating loop.
