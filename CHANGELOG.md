# Changelog

## [0.6.4] - 2026-11-13

Records that refuse wrong input. Tablet's records took what they were given: a message under another role's name, a review of a commit that didn't exist, one question to the owner filed twice, and 150 decisions that were only corrections. The owner's approval in a session, on the other hand, could not be recorded at all.

- **A message or review can't be filed under another role's name.** `softory coord message send` and `softory coord review add` refuse a `--sender` or `--reviewer` other than the calling role (`SOFTORY_ROLE`, which `softory start` exports) and name the fix. A shell that dropped the variable can't be checked this way; the scaffold's session check still applies there. Jade sent a message as Avery by mistake.
- **A review names a commit git has.** `softory coord review add` refuses an `--artifact` whose `commit:`, `head=`, or `base=` hash, or a bare hash, isn't a commit in the repository. An artifact that is a file or a link passes as before.
- **The owner's word in a session counts** (`softory ruling --review <ID>` and `--escalation <ESC>`). A ruling that names a unit is also recorded as the owner's accepted review of it, at the unit's commit, naming the ruling, who recorded it, and where the owner said it. A ruling that names an open escalation closes it and tells whoever raised it. The owner's digest lists both for a day with how to replace them. A role still can't write a review under the owner's name any other way. In Tablet the owner's chat approval of TASK-91 could not pass the owner-review gate, and an escalation answered in a session stayed open for days.
- **The owner isn't asked the same question twice.** `softory escalate` refuses a question that an open escalation already asks, and returns that escalation's ID. Darwin's 24px question was filed twice, five seconds apart.
- **A correction writes no decision.** `softory supersede` keeps its reason on the retracting evidence row. The decision log is for decisions again; 150 of Tablet's 250 were corrections.
- **A lost race in the database's path check is run once more.** SQLite removes its `-wal` and `-shm` files when the last connection closes, and the scaffold's check sometimes looked in between and failed. Softory, and `softory coord`, run the command once more when that is the error; nothing was read or written by then. The fix belongs in the scaffold (1.4.3).

## [0.6.3] - 2026-11-13

Verify once per commit. Tablet repeated checks it had already passed: the same commit was tested once per unit that named it, a UI unit failed for findings in lines it never touched, and STORY-21 ran its feasibility check 44 times, once per bug.

- **A commit that passed is not tested again.** `softory verify` at a commit whose ledger entry passed with the same verify settings (command, setup, retry, shared folders) reuses that pass and says so in `reused`. `--fresh` runs the tests anyway. A failed entry is never reused, a newer run always replaces an older one, and passes recorded before 0.6.3 are run once more because they don't name their settings.
- **A reused pass runs only what the unit still needs.** When the design detector applies to the unit and has no clean result for it at that commit, verify runs the detector alone, with no tests and no wait for the verify turn.
- **The design detector blocks only on lines the unit wrote.** A finding on a line the unit's own commits didn't change was there before the unit: it is counted in the result ("2 on lines this unit didn't change") and doesn't fail the verify. A finding with no line, or in a file git can't blame, still blocks.
- **A flaky test costs one retry, not a round** (`verify.retry`, empty by default). Set it to a command that reruns only what failed (`pytest --lf`, `playwright test --last-failed`). After a failed run it runs once in the same tree; a pass then counts, the first run's output is kept, the result says `flaky` and asks for one bug per flake, and `.coordination/softory/flakes.jsonl` logs it. A timeout is not retried.
- **A bug doesn't re-run its story's feasibility check.** The plan a verdict covers is the story and its tasks; a bug filed under the story repairs work the plan already holds. New tasks and changed requirements are still checked. Each open story with bugs is checked once more after the upgrade, because its plan fingerprint changes.
- **The owner is asked once per missing thing.** The digest lists each provisioning request once with the stories that need it, instead of once per story.

## [0.6.2] - 2026-11-13

Sessions the owner opens are first-class. Since 10 Nov, Tablet has run every role as a long-lived session with a heartbeat instead of runner runs, and softory hid work from those sessions. All from Tablet's BUG-157 and its related notes.

- **A session is told about its work during a pause** (attended mode). A pause stops the runner from starting roles; with `run.mode: attended`, `softory pending <role>` run by a session the owner opened now exits 0 when work waits, and says `paused_for: runner starts only`. In Tablet every check-in stopped on exit 3 for about an hour. In unattended mode a pause still stops check-ins, and the runner holds off in both. A scoped resume still limits the role to its tasks.
- **`softory pending` says which of four states it is in** (`state`): `work`, `running` (another session of the role is live), `paused`, or `idle`. Exit codes are unchanged.
- **A session sees mail sent to it.** An unread message addressed to the role counts for the role's own open session when it checks in, tagged or not, and `softory queue` shows the count. Four handoffs to Quinn sat unread for 90 minutes. The runner still starts nobody for an untagged note.
- **Quinn's session sees feasibility checks that are due.** The runner won't start a check beside a live Quinn session, so in Tablet nobody ran them. `softory queue` for Quinn lists each due story with the plan it would read, the plan the last verdict covered, and the command (`softory run-check STORY-n`); `softory pending quinn` counts them.
- **One open review record per reviewer and task.** `softory new review` refuses a second open record by the same reviewer for a task the first already names, and returns the first one's ID. Two workers under one Avery session opened REVIEW-329 and REVIEW-330 for the same commit.
- **`softory flow` leaves out what it didn't measure.** Sessions opened outside the runner log no minutes, tokens, or cost. While any worked in the window, runs, minutes, tokens, and dollars per unit and the idle share are empty, and `unmeasured` says why; time to delivery, review rounds, and disk still hold. Tablet's flow showed cost per unit falling for two days after its runner stopped. Sage's check-in also counts open sessions as the team having worked.
- **Stand-ins can start sessions and get a review workspace.** `softory start` and `softory workspace` accept an agent with an active stand-in grant; both refused Avery as an unknown role.
- **`softory coord` keeps `--actor` out of commands that don't take it.** It uses the flag to find the role's session, then drops it when the command's own help has no `--actor`. Greg's read calls failed five times in a row.
- **`softory new` prints the ID last**, so reading the tail of its output gives the right one.
- **Doctor doesn't call attended sessions a second scheduler** when `run.mode` is `attended`.

## [0.6.1] - 2026-11-13

The standards the owner set while running Tablet, now in softory, so every project gets them. Text, one charter setting, and one doctor warning: no new role, workflow, or kind of document.

- **Compare before choosing.** A new design or architecture choice shows at least three materially different options, including the simplest existing, native, or manual one, compared requirement by requirement, with one recommended. Design principle 9 said "at most three"; it now says this. The story spec and ADR templates carry an options table and a requirements table (each cell says Meets, Partly, Fails, or Unknown, with how and the evidence), and the comparison stays after the choice instead of being deleted. Epic briefs list requirements as user outcomes, so a requirement can't rule out an option by naming a technology. A routine bug fix needs no comparison. From Tablet: the Calendar design compared nothing against Google's private iCal address, which turned out to be the simpler route.
- **Sage looks for the simplest path before the build**, not after the owner notices. Sage's profile gains "Simplest path first": start from the user's first use, ask whether the work is needed before how well it is built, trace each constraint to its source, require a reason for every added user step, dependency, or delivery mechanism, judge whether the options are realistic, and say it once to the role that decides (Greg for product, Quinn for technical). Sage reads new epics, stories, designs, and ADRs at each check-in without waiting for a `process` review. Sage challenges and the owning role decides; no checklist, document, or approval is added. From Sage's own review of its work in Tablet.
- **A review or trial never needs a package**, export, or fresh environment (rule 10): it uses the development build of the recorded commit. Packaging happens only when the owner asks, or in `softory deploy`.
- **Peer review rotation** (`review.rotation`, empty by default). When several reviewers may give the same review, `softory reviewers` names one to `ask`: whoever already reviewed the unit, else the unit's number picks a place in the rotation, skipping builders. Requests spread across reviewers and stand-ins with no state to keep. Any eligible reviewer's verdict still passes the gate.
- **`softory doctor` names installed text someone edited.** The installer records the hashes of softory's skills, templates, workflows, and instructions, and doctor warns when one differs from the release. It is a warning, not a failure: the gate doesn't read these files, so work goes on. Reinstalling restores them. In Tablet a role rewrote 14 installed skill files in place and doctor passed in silence.

To use it in Tablet: discard the local edits in your softory checkout, pull, and reinstall. To spread peer reviews, approve `{"review": {"rotation": ["gold", "jade", "avery"]}}` with `softory charter approve <file> --merge`.

## [0.6.0] - 2026-11-11

Merge and ship to staging without you. Finished units reach the base branch on green, the base stays green, each merge deploys to staging with a smoke test, and releases have their own gate. Production stays yours. Built on scaffold 1.4.2, which lets the scaffold enforce the basics itself.

- **Scaffold 1.4.2** (`a62ee30` on `1.x`; tag `v1.4.2` pending). The installer turns on its strict policies in `.coordination/config.yml`: `closure_policy: strict` with `closure_review_waiver: decision` and `closure_exempt_tags: unit:review`, and `dependency_policy: strict`. A raw `task status done` now needs an accepted review from someone other than a builder and no open `blocks` dependency, and a claim on blocked work fails with `task_blocked`. Review records close as before (exempt tag), drops cite their decision, and `softory close` cites the gate's verdict as a decision where softory's rules differ from one accepted review (Greg accepting the story he owns, or changes requested with follow-ups filed). Finished dependencies are resolved on close. The gate fails closed (`config_intact`) if the policy lines change.
- **Stacks use `informs`.** `softory stack` links each member to the one below with an `informs` dependency, which means "built on" and never blocks a claim.
- **Stories and epics show as active** while their children run (`task activate`, gap S5). The runner sets and clears the marker each tick; `task list --active` lists them.
- **Merge on green** (`merge.by: softory`, off by default). `softory ship`, which the runner starts each tick, merges units that closed through the gate since you turned it on: up to `merge.batch_max` (5) become one candidate commit in a throwaway worktree, and the base moves only when `softory verify` passes there. A unit already on top of the base is a fast-forward, and its own verify counts. A failing batch is retried one unit at a time; a unit that conflicts or fails alone stays off the base and its builder gets a priority 1 bug. A unit built on another unit's commits waits until that unit closes too. `merge.push` names a remote; softory pushes only a candidate it verified, never a commit made on the base by hand. `softory pause` stops shipping too. With softory merging, roles' Claude settings deny pushing the base.
- **The base stays green.** Whenever the base moves, by softory or by hand, softory verifies it. A red base gets one priority 1 bug, pages you, and nothing else merges until that bug's fix does. A base moved outside softory while softory merges shows in the digest.
- **Deploy targets** (`deploy.targets`: `name`, `command`, `smoke`, `auto`, `timeout_minutes`). `softory deploy <target>` runs the command and then the smoke test in a clean checkout of a commit that passed verify, and logs it. `auto` targets get every merge; a failed deploy or smoke test files a priority 1 bug.
- **Release unit** (`softory new release`, `RELEASE-n`). It records the base commit it ships. Gold builds it, Toby and Quinn review it, and Greg closes it once it has a rollback plan (`--type rollback` evidence) and every target but production passed at its commit. `softory deploy production --release <ID>` takes a closed release, by you at a terminal, and deploys only the commit the release recorded.
- **Secret scan in the gate** (`no_secrets`): the lines a task or bug's own commits add are scanned for private keys, cloud and API tokens, hard-coded passwords, and secret files such as `.env` or `*.pem`. What a merge commit adds beyond git's automatic merge counts too. Placeholders and `secrets.allow` patterns don't count; you can waive a false positive. The charter's `secrets.stores` declares where secrets live and who reads them; softory never stores one.
- **Daily database backups** into `.coordination/backups/softory-daily-<date>.sqlite3`, keeping `backups.keep_days` (7).
- `task show` orders reviews by sequence in 1.4.2 (S23), so softory no longer re-reads them on same-second ties.

To use it in a project: reinstall, then approve `{"merge": {"by": "softory"}}` (and `deploy.targets`) with `softory charter approve <file> --merge`. Pause the runner while you reinstall, as for any scaffold upgrade.

## [0.5.11] - 2026-11-10

The tracker console can act again in a project with more than 500 sessions, and every list shows its newest rows first.

- **The tracker moves to `9e693fc`** (from `ee3dee6`). Its header read only the project's 500 oldest sessions, so in Tablet (937 sessions) the console's own session never loaded: the header said "No active session is selected for local-operator" and offered nothing to pick, and every action stayed disabled. The console now loads active sessions only (tracker UI-84). The new pin also brings the tracker's other changes since `ee3dee6`: an escalation can be resolved from its inspector, a blocked task shows what blocks it, a refused stale change shows what changed, the row-action column appears only when a row qualifies, and the Export page is gone. Softory used none of the Export page.
- **Two fixes in what the new pin brings** (tracker UI-85, from review of this release). "Since you loaded it" no longer counts changes from before the load when a record revisited a status (draft -> review -> draft). Resolving an escalation looks up a follow-up id the loaded list doesn't hold, so a real task past the first 500, or one created since, is no longer refused.
- **Newest first, with "Load older"** (tracker UI-86). Every list read the CLI's oldest 500 rows, so in Tablet Messages (Conversation and Ledger) never showed the newest messages. Messages, Tasks and every record list now read newest first and load older pages on request, and stay exact when rows arrive or leave underneath. Session recovery, End session, agent retirement and escalation follow-ups read every open task and active session before they trust the list. The board-change notice reads past heartbeats. "Why this is blocked" counts a session recovery as a new blocked episode, and never shows another task's cause.
- **Rulings show where they were made** (tracker UI-87). An escalation resolved under the Open filter, or opened by link, is read again by id, so the inspector no longer offers Resolve on a record already resolved. "Since you loaded it" counts changes after the record's last audit row read with it, not after a timestamp, so a change made before the load no longer shows as one since.
- **Previews that are complete or say they aren't** (tracker UI-88). The open-task read behind session recovery, End session and agent retirement no longer skips a task when another is finished mid-read, and a read that can't be made whole is refused: the sheet then says the claims or assignments could not be checked, not that there are none. "Since you loaded it" takes its audit position with each record as it is read, so a form opened on a stale row keeps the position of what was shown.
- **"Load older" stays exact under change, and an unread reason isn't an absent one** (tracker UI-89). When the list moves while older rows load, every page of the re-read is checked against the last row read, so no row is skipped or shown twice. "Why this is blocked" says the reason could not be read, with a retry, when its history fails to load; it used to say no reason was recorded.
- **A list read across pages is checked against the audit log** (tracker UI-90, UI-91). Two changes that cancel each other out, such as a completion and a reorder, could pass the page checks and drop a row. Every multi-page read, "Load older" and re-read is now accepted only when nothing but heartbeats was written while it ran, and is retried otherwise. When the audit log is too long to check to its end, the console treats that as unknown, not as quiet. The same holds when the audit position cannot be read at all: the list is read again, and is never shown as complete unverified (tracker UI-92).

## [0.5.10] - 2026-11-10

Simplification becomes a rule every role must follow, and a new role owns it. In Tablet, agents made their own process: 11 copies of the same plugin zip under `dist/releases` (one folder per commit, 28 MB), 66 untracked review documents in the main checkout, four leftover worktrees, a backup branch, a zip of cleanup records in evidence, and a 390-line untracked installer.

- **Rule 10, a MUST:** no zip, bundle, backup branch, or copy of the tree, and no new script, workflow, or kind of document, unless a unit's acceptance criteria need it. Proof is evidence rows plus `softory verify`. One checkout per role, and one release artifact that each build overwrites.
- **Sage, Software Development Manager** (`sage`, Claude), owns the delivery process, with simplification as its main job. Sage decides whether a new workflow, script, packaging step, generated artifact, or kind of document exists, reviews the new `process` tag (Quinn backs up), and checks in on the team's process, filing `simplify` units that remove the cause. Profile, roster, RACI (a new Delivery process table and a Sage column), boundaries (process versus architecture), and sources are updated.
- **`softory clutter`** lists untracked files, archives (ignored folders included), duplicate archive names, extra worktrees, and merged or idle branches. It is read-only, and the digest shows a line when it finds anything.
- **Sage's operating loop.** The runner wakes Sage for a check-in at most every `simplify.checkin_hours` (24), and only when the team ran, filed feedback, or left clutter since the last one, so an idle team costs nothing. Each check-in measures, looks for causes, files `simplify` units with a number to move, and cleans up. Its budget is 4 runs and 40 minutes a day.
- **`softory flow [--days 7] [--record]`** reports the process's numbers: median time to delivery, review rounds, runs, minutes, tokens and dollars per delivered unit, the share of runs that changed nothing, and disk used by logs, verify, workspaces, evidence, and archives. `--record` keeps a snapshot, and the next report lists what got `worse`.
- **`process_paths` gate check:** a unit whose own commits change `simplify.process_paths` (scripts, `bin/`, CI, Makefiles, Dockerfiles) must carry the `process` tag. A unit with no recorded commit (a PR link only) fails it until `softory commit` records one or it carries the tag; design units are exempt. The owner can waive it.
- **Clean handoff:** `softory handoff` refuses while untracked files that changed during the claim sit in the main checkout. Commit them, file them with `softory report`, or delete them. Set `simplify.clean_handoff` to false to turn this off.

## [0.5.8] - 2026-11-10

Runs the owner can watch and step into. Tablet's owner couldn't see headless runs in either app, or interject while one worked.

- **Attended mode.** With `run.mode` set to `attended`, the runner still decides who to wake and when, but opens each role's interactive harness (`run.attended`: `claude` and `codex` with the run's prompt, model, effort, and settings) in a tmux window, or in a Terminal window on a Mac without tmux. `softory attach` attaches to the tmux session. The prompt tells the role the owner may type to it and to run `softory end` when done.
- **How an attended run ends.** An interactive harness doesn't exit on its own, so the run ends when the role ends its session, the harness exits or its window closes, or at `minutes_per_run`. The runner stops what is left, closes the window, and hands back unfinished claims, as for a headless run. The run's log keeps a copy of the window. Budgets count runs and minutes only, since interactive harnesses don't report cost.
- A feasibility check stays headless in attended mode: it is a one-shot verdict that wouldn't end its own window.
- `softory charter` checks `run.mode`, and that attended mode has an interactive command for every harness the models use. `softory run` reports where attended runs open.

## [0.5.5] - 2026-11-09

The rest of the Tablet review's fixes that don't wait on more data: work waiting on the owner stops waking roles, reviewers stop copying the tree, and evidence leaves the main checkout.

- **Holds.** `softory escalate --holds TASK-n,...` takes the named units off every queue, ready-to-close and `pending` while the escalation is open (TASK-59 to TASK-71 kept waking roles on an open owner question). The answer, or the default for an undoable escalation, releases them, and their builders wake on it. `softory defer <ID> --decision <id> [--until YYYY-MM-DD]` does the same on an owner's decision, until the date or `softory defer <ID> --lift`. `softory queue` lists held units under `held`, with why. The tracker isn't touched: status and claims stay.
- **Review workspaces.** `softory workspace <role> [commit]` keeps one checkout per role under `.coordination/softory/workspaces/`, moved to the commit asked for, with the charter's `verify.share` folders linked. It is a worktree where git allows one and a snapshot where a sandbox protects `.git`. The code-review skill says the verify result is the test proof: don't rerun the suite or copy the tree to /tmp (Jade, 9 Nov).
- **Reports outside the checkout.** `softory report <ID> <file>` files a report or screenshot under `.coordination/softory/evidence/<ID>/` and records it as evidence; an untracked file is moved. `softory verify` warns when the main checkout has changed or untracked paths (Tablet's had 66).
- **The reference check at handoff.** `softory handoff <ID>` moves a claimed unit to review only with evidence and, for a `ui` unit, its rendered check against the design reference; `softory coord task release <ID> --to review` applies the same check. A `ui` unit already in review without one wakes its builder, not its reviewers (Greg, 9 Nov: five fixes stalled at close).
- **The charter names each role's harness.** `softory start <role> --harness X` refuses a harness the charter doesn't run that role on (a Codex Jade review after the owner ruled Jade runs on Claude, TASK-72). The owner allows more in `models.<role>.also`. Runner-started runs aren't affected.
- **`softory gc [--days 14] [--dry-run]`** removes workspaces unused for that long, run and verify logs older than that, and verify trees a crashed run left in the temp folder. Evidence files stay.
- **Amending a story's criteria** is written down in work-units.md: record the decision, then a revision-checked `task update`, no claim (STORY-16).

## [0.5.4] - 2026-11-09

From Tablet's logged feedback (29 notes, 303 runner runs from 5 to 9 November, $154.52). One operating loop for every harness, and fewer runs that buy nothing.

- **A stack close runs every check.** `softory close <ID> --stack` evaluated each member's gate without the objective checks, so a stack could close code softory never saw pass its tests, or reach outside its lane (Quinn, REVIEW-248; BUG-50 and BUG-51 closed this way). Members now get `verified` and `lane_paths` like any close.
- **The runner owns the session.** Unattended Claude runs lost `COORDINATION_SESSION` after the first command, because each Bash call is a fresh shell, so `softory close` failed with `session_required` even when the gate passed (REVIEW-242, REVIEW-256). The runner now opens the role's session, passes it to the harness in its environment, and ends it after the run. The prompt no longer asks the agent to start or end one.
- **Sessions survive fresh shells.** `softory start` remembers the session per role. Commands with `--actor`, and `softory coord` commands naming `--agent` or `--actor`, use it when no session is set. `close`, `drop`, `stack`, and `end` take `--session`.
- **Runtime state moved to `.coordination/softory/`.** Codex's `workspace-write` sandbox refuses writes under `.agents/` (confirmed on Tablet: "Operation not permitted"), so Codex roles couldn't record feedback, and their notes were lost. The run log, verify ledger and logs, escalations, decisions state, proposals, feedback, and sessions now live beside the database. The installer moves them; reload the runner after upgrading so launchd's log follows.
- **Verify falls back to a snapshot** when `git worktree add` is refused, since the same sandboxes protect `.git`. It checks out every tracked file through a throwaway index outside `.git`, not `git archive`, which honors `export-ignore` and could drop a repository's tests.
- **Messages wake a role only when they need it.** Unread messages started 199 of Tablet's 303 runs ($83) and 109 of those changed nothing, largely acknowledgements that woke the sender back. A role now wakes for a message from the owner, one with an action tag (`request`, `question`, `ruling`, `answer`, `blocker`, `urgent`), or one naming a unit it builds, holds, reviewed, or owes. Other messages wait for the next run, or wake it after `retry_hours` with no run. The instructions say not to send acknowledgements.
- **The queue lists only reviews a reviewer owes.** A requirement another listed reviewer already accepted no longer shows on every stand-in's queue (Avery saw 15, BUG-113), and a reviewer who asked for changes isn't woken again until new evidence lands or wrong evidence is retracted (TASK-63).
- **A run that stops mid-task hands its claim back.** The scaffold won't end a session that owns claims, so a harness that exited or timed out holding a task left it in progress until stale-session recovery blocked it. The runner now waits for a timed-out or interrupted harness to exit (SIGTERM, then SIGKILL to its process group after 30 seconds), releases each claim to `todo` with a note, then ends the session; if it still won't end, the session stays remembered for `softory end --actor <role>`.
- **Evidence in the same second as a review** is ordered by the audit log, so a builder's fix that lands within a second of a changes-requested review still puts the task back on the reviewer's queue.
- **An actionable message past the first 100 unread** still wakes the role: `pending` reads on, page by page, until a message needs the role or the inbox runs out.
- **Spend per closed unit.** Each run logs how many records it changed besides bookkeeping. `softory usage` adds `last_7_days` and the digest adds a section: runs, dollars, units moved to done (from the audit log, so edits to old work don't count), dollars per closed unit, and the share of runs that changed nothing.

## [0.4.2] - 2026-11-01

From the field report on softory in six projects, mostly Vault Radar's 12 to 30 October: about 45 sessions and 66 messages per delivered task, 39% of reviews asking for changes, 31 units stopped at the review cap, and a 22-minute test run that agents booked by message. This release fixes the parts that need nothing new from the scaffold, so the Vault Radar runner trial measures the runner, not these.

- **Review records don't count toward the round cap.** A review run's verdicts are its output, so ten of Vault Radar's 31 stopped units were review records counted next to the task they reviewed. They leave the cap and the digest's stopped list.
- **Missing evidence costs one free round.** Reviewers label an item `evidence:` when the work is right and the proof is missing. A request whose every item is `evidence:` doesn't count, once per unit (`task_caps.free_evidence_rounds`). Ten of the owner's Vault Radar rulings were "one more bounded cycle", mostly for screenshots.
- **A stuck unit isn't reassigned.** The digest offers split, drop, or one more round for a unit at the cap. Each role keeps its own work; reassignment stays for the edge cases in `boundaries.md`.
- **Re-reviews stay scoped.** `softory-code-review` says a later pass checks the last pass's blocking items and the new diff only; anything new outside that diff is a follow-up, not a block.
- **Verify runs one at a time, in its own queue.** A second `softory verify` waits on a lock and shows in `softory queue`, so roles stop booking the test machine by message (TAKE appeared in 621 Vault Radar messages, RELEASE in 1,765).
- **Verify can't break the main checkout.** Shared folders are cloned copy-on-write (`verify.share_mode: clone`, the new default) instead of linked, so an `npm ci` in the test tree no longer deletes the main `node_modules`. `link` keeps the 0.4 behaviour.
- **Verify failures keep what reviewers need.** A failed run keeps its whole log and copies `verify.keep` globs (traces, screenshots) to `run/verify/<ID>-<sha>/`. On macOS the run holds `caffeinate -i`, so the Mac doesn't sleep under it. `verify.setup`, when set, runs first, and its failure is recorded as a setup failure, not a test failure.
- **Commit evidence names one commit.** `softory commit <ID> <sha> [--base <sha>]` writes `commit:<full hash>;base=<full hash>`. Free text that names several commits is now skipped as ambiguous, so a base commit's passing tests are never credited to the head (BUG-53).
- **Wrong evidence can be retracted.** `softory supersede <ID> <evidence> --reason ...` records a decision and a marker row; the gate, the review-record check, and `verify` read past the retracted row, and the audit keeps it. Its adder, Quinn, or the owner may do it.
- **Escalations read at a glance.** `softory escalate` takes `--issue` and one `--ask` question, and refuses text over the limits or with words fused to numbers ("contain9", "runnerusage0"). The digest shows each ask in full instead of cutting it at 160 characters, and counts escalations owned by any of the owner's names (`owner_aliases` in the charter), since Vault Radar's used `owner`, `Josh`, and `josh`.
- **Scoped resume.** `softory resume --task <ID> --roles a,b` keeps a pause but lets those roles work on that one task, so the owner can restart one piece of work after stopping everything. The run's prompt, `queue`, `close`, and `close --ready` stay inside that task, and any later `pause` covering the role revokes the grant.
- **Charter approvals show the change.** `charter approve` prompts with one line per setting that changes, does nothing when nothing changes, and `--merge` adds to the approved settings instead of replacing them. Vault Radar's charter was approved seven times in two days.
- **Sessions name their model.** `softory start` fills the harness and model from the charter when they're left out; 3,240 of Vault Radar's 4,543 sessions had none.
- **Usage counts every session.** `softory usage` adds `sessions_today` per role, whatever started the session. `softory usage --team [--days N]` reports sessions and messages per delivered task, and for each reviewer how many requests for changes were followed by new code.
- **The digest flags churn.** An open unit whose record changed `waste.revision` times (default 30) without closing is listed, a sign of a role repairing its own tooling instead of the task (BUG-33 reached 61).
- **Doctor checks the scheduler.** With a charter approved, `softory doctor` warns when no launchd job or cron line runs softory, or the runner hasn't ticked in 30 minutes; `softory setup` checks the schedule step instead of always calling it manual. Vault Radar's launchd job was written and never loaded. The instructions now tell any scheduled check-in to run `softory pending <role>` first and stop on exit 3.
- **`close --ready`** closes every unit the actor may close that passes its gate now, for clearing a backlog of finished work.
- **Triage reads what a task holds.** A task named `...-REVIEW-...` that delivered a commit is built work, not a review run to adopt.
- **A design lane.** `lane:design` tasks and bugs are Darwin's; Greg's product review replaces peer code review, and `softory verify` doesn't apply.
- The owner-prompt tests run on macOS too: BSD `script` sent end-of-file before the typed answer, so they use a small pseudo-terminal runner there.

Not in this release: typed handoff records and broadcast recipient clean-up (0.5.0 planning), and moving approvals off the terminal, which waits for 0.5.0's recovery work.

The owner overrides any of them once with `softory charter approve <file>` at a terminal; the overrides live in the hashed `local.json` and are recorded as a decision. `softory charter show` prints what is in force.
- **Runner.** `softory run` is one tick for launchd or cron. It starts a role only when `pending` says it has work, it's under today's budget, and it isn't paused or already running, and it pages what is due. `softory run-role` runs the harness with a time limit and logs each run to `.agents/softory/run/runs.jsonl`, which the budget counts. The prompt is a few lines naming what is waiting. `softory schedule` writes the launchd job.
- **Budget, caps, and a kill switch.** Daily runs and minutes per role, and minutes per run, with per-role overrides (`budget.roles`). Defaults: 24 runs and 120 minutes a day, 30 a run; Greg, Darwin, and Toby get shorter runs and 60 minutes a day. A task with `escalate_model_after` rounds of requested changes runs on the role's stronger model; at `review_rounds` it drops out of `pending` and goes to the owner. `softory pause` (anyone) and `softory resume` (owner, at a terminal); `pending` honours a pause too. `softory usage` shows today's use.
- **Tests and lanes in the gate.** `softory verify <ID>` runs the charter's `verify.command` at the unit's newest commit in a throwaway worktree and keeps the result in softory's own ledger. With a command set, a task or bug needs a pass there (`verified`); an evidence row an agent writes doesn't count. With lane paths set, `lane_paths` fails a diff outside the lane unless the task is tagged `cross-lane` and Quinn accepted it. Both checks are off until the charter sets them, and both are waivable by the owner.
- **Digest and paging.** `softory digest` lists what needs the owner: proposals, escalations to the owner, capped tasks, unread messages, silent and paused roles, and budget warnings. A unit closed without the gate, or a role over budget, pages at once (once a day each, outside quiet hours); the rest goes in one daily digest, to the owner's inbox and through `paging.command`.
- **Permissions per role.** Claude Code roles run with a generated settings file: edits only in their lane's paths or their docs folder, the coordination and git commands they need, and never softory's or the database's files.
- **Builders hear about requested changes.** `pending` now wakes a builder whose task in review got a "changes requested", instead of waiting for a message.
- **Models from role-fit benchmarks.** Darwin, Quinn, Jade, and Gold default to Claude Opus 5.5, which leads Terminal-Bench 4.0 (64.8%) and the WebDev Arena (1807). Toby and Greg default to Codex with GPT-6 Astra, which leads SEC-Bench Pro (85.4%) and ties Opus on CWE-bench (68% to 67%). A cheaper Sol setup with escalation is documented for tight budgets. [docs/models.md](docs/models.md) has the sources.
- **Less wasted work per run.** Reviewers aren't woken until `softory verify` passed at the commit (the builder is woken to fix the tests instead), and wake in batches: at `review_batch.min` waiting reviews (2) or after `review_batch.max_wait_minutes` (60), clearing all of them in one run. The prompt carries each waiting unit's title, acceptance criteria, requested changes, and changed files, with the fixed rules first so the prompt cache applies. Effort follows the job: `effort.review` (medium) for runs with only reviews, closes, or messages, `effort.build` (high) otherwise, with a per-role override.
- **Real tokens and cost.** Runs log input, cached, and output tokens and dollars from each harness's own report (`--output-format json` for Claude Code, `--json` for Codex; Codex dollars are estimated from `prices`). `softory usage` totals them. Optional `usd_per_run` and `usd_per_role_per_day` caps, off by default.

- **`softory setup`** checks the owner's one-time steps and says what is left.

## [0.3.0] - 2026-10-23

From the owner's eight points after a week in Vault Radar, and an independent review of 0.2.0. Don't install 0.2.0; install this.

- **Review records.** A review run kept as a task is a record of the reviewer's output. Its own verdicts never block it, nobody reviews it again unless a tag on it needs a reviewer its author isn't (a `security` record by Avery needs Toby's sign-off, unless Avery stands in for Toby), and a "changes requested" on it counts as handled once it names follow-up tasks that exist, or its reviewer later accepts. It must hold reports and no code, name what it reviewed, and not review its reviewer's own work. It closes from review, blocked, or todo. On a copy of Vault Radar's database from 2026-10-23, 28 of the 34 open review runs pass the gate after `adopt`. Five link to nothing they reviewed and need `--for` (three of those look like ordinary tasks, not review runs), and one holds on a product objection with no follow-up task.
- `softory adopt <ID> --unit review` reads what a run reviewed from its `informs` links, leaving out other review runs and the reviewer's own work. Only the run's reviewer or the owner may ask, a task with code evidence is refused, and nothing changes until the owner approves: `softory approve --all` takes every waiting adoption after one typed yes and records one decision for the batch. The prompt lists anything not tagged or named as a review run first, and stand-ins and waivers are never part of `--all`. Otherwise a builder could relabel their own unreviewed fix as a review and close it.
- **Named backups can't be gamed.** The backup reviewer applies only when the specialist alone built the work. Adding Toby as a co-assignee no longer moves the security review to Quinn. A role-wide stand-in for the specialist doesn't count on the specialist's own work; one scoped to that task does. (In Vault Radar, Avery's role-wide stand-in for Toby had silently become the reviewer of Toby's own threat model.)
- **Scoped stand-ins.** `softory standin add <agent> --for <roles> [--task IDs] [--until YYYY-MM-DD]`. Grants that name tasks apply only there, and an end date lapses on its own. `standin list` shows each grant and whether it's active; `standin remove <agent> [--for roles]` takes back some or all. Older `local.json` files still read.
- **Dropped work.** `softory drop <ID> --reason ... [--superseded-by ID]` closes a unit nobody will build, with a decision, evidence pointing to it, and `resolution:` tags. Droppers are in `gates.json`. `softory tree` shows `done: won't do` or `done: superseded by ...`.
- **Stacks.** `softory stack <bottom> ... <top>` groups work built on other unfinished work. `softory close <top> --stack` checks every member's gate with the other members counted as done, and closes them bottom first only if all pass. The coordination CLI has no transactions, so if a close call itself fails partway, softory stops and reports what it closed (`closed_before_error`).
- **Follow-ups don't block their source.** `softory new bug --from <ID>` links back with `informs`. `--blocks-source` keeps the 0.2.0 behaviour when it's needed.
- **Silent roles.** `softory silent [--hours 12] [--notify]` lists roles with work waiting and no session for that long, or ever, and messages the owner once a day per role. `triage` includes it. The README shows a launchd or cron line with a desktop notification.
- `softory pending` no longer strands work after a crashed run: any waiting work counts again once `--retry-hours` (default 4) pass without a run.
- **Owner rulings.** `softory ruling --title ... --decision ... --where ...` records a decision under the owner's name, marked "recorded by <role>" with the session and where the owner said it.
- **Owner approval.** `standin add|remove` and `softory approve [IDs | --all]` run only at a terminal, after a typed yes. Agents ask with `softory propose standin|waiver ... --why ...`, which records a proposed decision and grants nothing. A waiver lets one review check pass on one task, and the gate shows it.
- **Rules don't drift by accident.** The installer makes `gates.json`, the role files, softory's code, and `local.json` read-only and records their hashes. The gate fails closed (`config_intact`) and `doctor` names the file when one changes. This catches mistakes, not a determined agent: the hashes sit in `manifest.json`, and a terminal can be simulated.
- **CLI.** `softory inbox` lists unread messages with the number that marks exactly those read (`--mark-read N`); the operating-loop skill no longer says `--cursor HEAD`, which the scaffold rejects. `softory message <ID>` shows one message. `softory all <entity> list` follows every page past 500 rows, and the gate's review lookups page too.
- `triage` recognises `code-review` and `independent-review` tags as review runs, and suggests each run's adopt command.

- Units of work: epic (project), story (feature), task (function), and bug (fix), with templates and flows.
- Nine skills: operating loop, code quality, testing, code review, secure coding, design, product spec, architecture, and token economy.
- `softory` CLI: `start`, `new`, `tree`, `adopt`, `queue`, `reviewers`, `gate`, `close`, `standin`, `triage`, `link`, `worktree`, `coord`, `end`, `feedback`, `roles`, `doctor`, `tracker`, `sync`, `skills`, `uninstall`.
- Installer that adds scaffold 1.4.0 (SQLite) and the tracker, registers the roles, and hides everything with `.git/info/exclude`.
- A catalog of recommended open-source skills, pulled at pinned commits.
- Git worktrees: `softory worktree add` and `softory link` symlink softory into a worktree, hidden by the shared exclude rules; `--share` links installed dependencies too; `softory coord` runs the coordination CLI against the main database from anywhere; `softory end` ends a session; the CLI finds the main checkout from any worktree.
- `softory feedback` lets agents log friction with softory itself to `.agents/softory/feedback.jsonl`, and the instructions ask them to.
- `softory triage` lists open tasks that already have an accepted review. `softory doctor` flags an `AGENTS.override.md` that is out of date. The installer reports an existing scaffold and refuses to downgrade a 2.x one, and `uninstall` leaves a scaffold the project had before softory.
- Joining a project that already has a team: `softory standin` for existing agents, a minimum `legacy` gate for tasks created before softory, `softory adopt` to move them into a story, and no repeated scaffold block when the project's `AGENTS.md` already has it.
